## 实现与约束核对

- 只包含 `rtk_demux.h` 与 `<string.h>`；无堆分配、VLA、递归、浮点、日志、平台头或 OS 调用。
- 初始化建立首字节位图；空闲流扫描按字节查表，连续未知输入直接使用调用方指针回调。
- 按 `need` 整段复制，补足后才调用 `step`；逐字节喂入合法六字节帧时自测验证仅调用两次 `step`。
- 同一起点按优先级尝试候选，回放从前缀 1 开始按 `need` 递增，不直接把整个缓冲区交给新候选。
- 所有候选拒绝后前移起点；缓冲区中的未知字节合并输出。回放在中途成帧时，先输出前面的未知字节，再输出帧，回调结束后才 `memmove` 剩余字节。
- `abort` 保留当前起点的已拒绝候选集合，直接拒绝当前半帧，继续回放其他候选和后续起点；空闲 abort 不累加 aborts。
- `need == 0`、超过 `max_frame`、未知 step 枚举均按拒绝处理；超过容量另计 overflows。容量判断用减法，已覆盖 `SIZE_MAX`，避免加法回绕。
- 帧与未知字节回调中分别验证 `feed/abort/init` 返回 REENTRY，且回调中的字节内容保持不变。
- 初始化之后位图不变，描述符不被写；自测验证 `feed/abort` 不再调用 `first_byte`。
- 所有窄化有范围或模计数解释；所有内部函数为 `static`；公共函数标明线程/ISR 约束。

## 阻塞项与争议证据

### 1. 首次 init 的初始化状态契约缺口（引擎当前限制，需架构方裁定）

冻结 `rtk_demux.h:112` 规定 init 初始化或重新初始化实例，`rtk_demux.h:108` 又要求在同实例回调中 init 返回 REENTRY；头文件和 ADR 均未规定首次 init 前必须把实例初始化为零。实例允许由调用方在栈上分配。

当前实现为保护回调状态，在清空实例之前读取 `dmx->in_callback`。`first_init_probe.c` 对尚未 init 的实例用 `memset(..., 0xA5, ...)` 设置初始存储后调用 init，UBSan 明确报告：

```text
components/rtk_demux/rtk_demux.c:163:12: runtime error:
load of value 165, which is not a valid value for type '_Bool'
```

即使按字节比较 bool 的对象表示可以避免上述非法 bool 读取，也无法区分“尚未初始化但字节恰好相同”与“实际回调中”的状态；不能宣称这解决了语义缺口。直接先清空实例又会破坏回调中的重入保护。引入全局实例/回调注册状态还会增加跨实例并发、ISR 与生命周期约束，不能默默替代冻结接口的实例内设计。

**因此目前仅验证了零初始化实例的首次 init。建议架构方明确首次 init 前的零初始化要求，或修订独立初始化/重初始化契约；G1 不修改冻结头文件，也不把该要求擅自当成已批准契约。** G3 的 `test_two_instances_independent` 同样声明了未初始化的栈对象 `dmx_b`；该次运行碰巧通过不能消除本风险。

### 2. G3 中途成帧案例的期待与优先级语义不符（测试争议）

执行时 `test_demux_engine.c:575` 的 `test_same_first_byte_priority_and_midbuffer_replay` 在输入：

```text
AA 33 66 AA 22 99 44
```

后期待 `busy == false`，并立即得到两帧。第一帧由 p2 在前三字节恢复后，余下 `AA 22 99 44` 必须按新起点处理：p0 在该新起点仍为最高优先级，其 `step` 明确在前缀不足六字节时要求凑满六字节，尚未 REJECT。ADR §3.1–3.3 只允许当前候选 REJECT 后换候选，因此此时正确状态仍为 busy，不能提前提交 p1 的四字节帧。

再喂入足够字节使 p0 拒绝，或由测试调用 abort，才可切换到 p1。G1 未修改测试、未放宽断言、未改变引擎优先级规则。

### 3. G3 生成器自测与严格编译问题（不属于 G1 引擎）

- `test_demux_stream.c:507` 的窄化告警导致两种完整构建失败，见上述原始命令。
- `test_demux_gen.c:46` 的 `test_xor_and_ubx_ck` 报 `Expected 0xE9 Was 0x10`，属于测试辅助生成器/已知向量分支，不调用 G1 引擎；G1 未修改或进一步替 G3 调整该向量。

### 4. clang-tidy 的 Annex K 建议

最终 clang-tidy 仅剩五处 `clang-analyzer-security.insecureAPI.DeprecatedOrUnsafeBufferHandling`，分别要求将 `memmove`、三处 `memset`、`memcpy` 换成可选 Annex K 的 `_s` 接口。G1 任务明确要求原地 `memmove` 与批量 `memcpy`，目标为仅依赖标准 C11 基础库的跨 MCU 引擎，不能假定这些可选接口可用。未关闭告警、未修改冻结配置、未加 suppress 注释。该项机械结果如实记为 FAIL，具体告警日志在 `test/demux_dev/g1/tidy.log`，请验收方判定规则适用性。

较早的 clang-tidy 数组边界推断告警在补充候选索引边界检查后消失；GCC `-fanalyzer` 最终无告警。
