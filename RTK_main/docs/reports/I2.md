## 2. 功能实现对照

| 需求项 | 实现位置与细节 |
| --- | --- |
| 蓝牙连接（PHONE 角色） | `BtSession`：默认 `--addr F8:B3:B7:25:D8:B2 --channel 1`，`socket.AF_BLUETOOTH` / `socket.BTPROTO_RFCOMM`；发送超时设 5.0 s 避免流控误触发超时，独立 `RxThread` 使用 `select.select` 轮询接收。 |
| RTCM3 帧与 CRC-24Q | `crc24q()`（0x1864CFB 查表）+ `crc24q_bitwise()`（逐位参考实现），启动即校验 `"123456789" -> 0xCDE703`；`build_rtcm3_frame()` 生成 `D3` + 保留位 0 + 10 bit 长度 + 载荷首 12 bit 大端消息号 + 3 B 大端 CRC-24Q。 |
| 真实基站历元与速率模式 | `build_rtcm_epoch()` 每历元构造 `1005(19 B)`、`1074/1084/1094/1124(各 100–400 B 随机)`、`1230(8 B)`；支持 `--epoch-hz` 历元平滑、`--burst` 历元整组一次性 `sendall`、`--rtcm-rate BYTES_PER_S` 恒定字节率步调发送。 |
| 产品负载交错与匹配 | `--product off|cycle`：`off` 时不发任何产品帧；`cycle` 时在 `rtcm reset` 前先发 `0x01` 学习定值应答，测试期间交错发 `[0x07 SET(44 B), 0x07 QUERY(回显 48 B), 0x01 QUERY]`，单发送线程写避免流边界交错，`ProductStreamParser` + `evaluate_product_replies()` 顺序对齐统计 RTT p50/p95/p99、丢失与内容错。 |
| 发送端顺序 CRC32 累计 | 按发送顺序对全部 RTCM 线路帧累加 `zlib.crc32(..., prev) & 0xFFFFFFFF`，与板端 `RtcmForwarder` 的 `rtk::proto::crc32` 算法及顺序完全一致。 |
| 串口板端计数解析 | `SerialConsole`（`--serial /dev/ttyACM0`，115200）：捕获串口占用/权限异常给出清晰中文提示；测试前发 `rtcm reset\r` 与 `status\r`，测试后等待 1.0 s 排空再发 `status\r`；清洗 ANSI 转义码后用 `RTCM_LINE_RE`（ADR-0006 §2 `rtcm:` 行）与 `STATS_LINE_RE`（`stats:` 行）提取全部字段。 |
| 判定与摘要输出 | 输出人类可读汇总表与 JSON 摘要（含 `rtcm_frames/bytes/crc32 match`、`rx_dropped_delta`、产品 RTT/丢失、实际发送/接收吞吐 B/s）；无 `rx_dropped` 且计数/`crc32`/产品异常即 `FAIL`（退出码 1），有 `rx_dropped` 时标记 `OVERFLOW_DROPPED` 并说明溢出丢字节导致 `crc32` 不匹配属预期。 |
| `--scan` 扫描 | `SCAN_RATES_BPS = (2000, 5000, 10000, 20000, 40000)` 依次各跑 `--duration` 秒并汇总吞吐/丢弃表。 |
| `--selftest` 离线自检 | `run_selftest()` 离线验证 CRC-24Q、RTCM3 帧结构与历元、产品帧乱片/垃圾/坏 CRC 重同步与顺序匹配（含丢帧检出）、含 ANSI 码与异步日志干扰的控制台正则解析、PASS/FAIL/OVERFLOW_DROPPED 三类判定。 |

## 5. 修正记录

### 2026-04 尾部排空与 RFCOMM 优雅关闭修正

- **原因**：原 `tools/hil/spp_rtcm_mix.py` 在 `--serial none` 且 `--product off` 时，`run_single_stage()` 仅在 `product_mode == "cycle"` 或 `console is not None` 时才等待排空，导致发送循环结束后未作任何等待即直接进入 `BtSession.close()` 并执行 `shutdown(SHUT_RDWR)` + `close()`。Linux RFCOMM 此时会丢弃内核发送队列中尚未发送完毕的末尾数据；实测 10k/40k B/s 速率下板端恰好少收到最后 1 帧（且 `rx_dropped=0`、`unknown_bytes=0`，证明末帧字节从未到达板端）。
- **改动**：
  1. `tools/hil/spp_rtcm_mix.py`：新增 CLI 参数 `--tail-wait`（默认 `1.5` s，不允许负数），`run_single_stage()` 在发送结束后先等待在途产品应答回完，并确保无论是否有串口或产品负载均至少等待 `tail_wait_s` 再读取板端 `status` 及返回关闭会话；在输出 JSON 摘要中记录 `tail_wait_s`。
  2. `tools/hil/spp_rtcm_mix.py`：`BtSession.close()` 改为先调用 `sock.shutdown(socket.SHUT_WR)` 并短暂等待（`0.2 s`），再请求停止 `RxThread`、执行 `shutdown(SHUT_RDWR)` 与 `close()`；并在 `run_selftest()` 中补充 `--tail-wait` 默认值/解析及 `BtSession.close()` 调用顺序的离线自检。
  3. `tools/hil/README.md`：在“主要 CLI 参数”表与“核对与判定规则”中同步 `--tail-wait` 参数说明及测试后排空/优雅关闭流程。
- **验证**：

  - `~/.espressif/python_env/idf6.1_py3.14_env/bin/python -m py_compile tools/hil/spp_rtcm_mix.py`：**PASS**（exit 0）
  - `~/.espressif/python_env/idf6.1_py3.14_env/bin/python tools/hil/spp_rtcm_mix.py --help`：**PASS**（`--tail-wait` 选项正常）
