## 2. 关键实现决定

- **LinkManager**：`Actions` 在 `on_open`/`on_frame`/`tick` 入口先 `clear()`；拒绝时把该 handle 写入 `Actions`；白名单满且收到新 HELLO 时断开；配对窗口只在 `tick` 中按 `>=` 关闭，HELLO 提升时若地址已存在不重复加入。
- **CommandDispatcher**：
  - 未知 ID 与 5.4 保留 ID（0x1E、0x21–0x25、0x28–0x34）在角色检查前返回 `kNoReply`；
  - 0x01 设备信息按 §4 的**显式偏移**写入（`fw_ver` 与 `board` 之间有 8 B 保留区，`board` 在 56，`radio_type` 在 96），不是简单顺序拼接；
  - 0x0D 设置按 5.4 行为不回复；0x07/0x14/0x15 均先检查 payload 长度；0x14 在 payload <18 B 时保留 `[17]=0x05`；
  - 0x40 查询的 `seq=0`、`fix_quality=0xFF`、`uptime=now_ms`、flags bit0=PHONE 在线/bit1=测试覆盖；
  - 0x44 清空白名单置 `reply.whitelist_changed`；查询返回 `count + n×6` 字节。
- **LinkService**：
  - `on_data` 严格 4 步：`on_frame` → 执行断开动作（当前句柄被断开则丢弃本缓冲区剩余字节并返回）→ 分发/写回 → 白名单/心跳；
  - 槽位释放时把解析器错误计数累加到 `retired_*`，新槽重建解析器，保证累计值单调且不重复计数；
  - 推送首次 `tick` 即到期，之后按无符号差值 `>= 1000 ms`，每轮（有 ALARM 时）`seq+1`。
- 不使用堆、不使用 IDF 头文件。

## 5. 未解决问题：clang-tidy 与冻结头文件的冲突（需验收方裁决）

`clang-tidy -p build-host components/rtk_core/*.cpp` 的 3 条发现全部指向**冻结头文件**：

```
components/rtk_core/include/rtk/core/command_dispatcher.hpp:65:25:
  error: 115200 is a magic number [readability-magic-numbers,-warnings-as-errors]
components/rtk_core/include/rtk/core/command_dispatcher.hpp:105:7:
  error: class 'CommandDispatcher' defines a copy constructor and a copy assignment operator
  but does not define a destructor [cppcoreguidelines-special-member-functions,-warnings-as-errors]
components/rtk_core/include/rtk/core/link_service.hpp:33:7:
  error: class 'LinkService' defines a copy constructor and a copy assignment operator
  but does not define a destructor [cppcoreguidelines-special-member-functions,-warnings-as-errors]
```

- 这 3 处位于 `components/*/include/**`，AGENTS.md §4 规定一个字节都不能改；`NOLINT` 只能写在诊断所在文件（头文件）内，无法从 `.cpp` 屏蔽。
- `.clang-tidy` 的 `HeaderFilterRegex` 覆盖 `components/`，因此头文件诊断必然出现；`.clang-tidy` 本身也是冻结文件。
- 使用 `--header-filter='^$'` 时本任务全部 `.cpp` 为 0 条，说明实现代码没有静态分析发现。
- 需要验收方选择其一：允许这 3 条冻结头文件基线的例外；或授权修改冻结头文件/`.clang-tidy`（例如增加 `NOLINT` 或调整 `HeaderFilterRegex`）。
