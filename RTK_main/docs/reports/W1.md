# W1 射频模式框架

分支 `feat/w1-radio-mode`，基线 `08a9be8`。目标为经典 ESP32，使用 ESP-IDF v6.1 和 Xtensa GCC 15.2。

## 接口与运行行为

- `requestRadioMode(RadioMode, RadioReason)` 用 CRC-8 保护一条 4 B 的 RTC 保留记录，再调用 `esp_restart()`。启动步骤 `radio` 位于 `earlyConfig` 和 `contexts` 之间。它读取并清除记录，只接受来自软件重启的有效请求。无有效请求时选择蓝牙并显示 `reason=default`。
- Wi-Fi 配置模式在启动时释放 BTDM 控制器内存。释放失败时以 `radio:bt_mem_release` 降级。模块清单使该模式跳过 `bt_link`、`rtcm` 和 SPP 专用缓冲及驱动的装配。GNSS 初始化所需的 RTCM 管道仍由启动分配器提供。
- 链路执行器继续服务存储、系统与已启用的调试模块。Wi-Fi 配置模式按执行器的 20 ms 空闲等待间隔唤醒，队列已有工作时直接处理。蓝牙模式原有的 SPP 唤醒保留。
- 启动日志、`status sys` 和 DEV 的 `radio` 查询输出 `radio=bt|wifi reason=…`。DEV 中的 `radio wifi`、`radio bt` 输出 `OK`，最多等待 UART 排空 500 ms。排空成功后重启，失败则输出串口错误并留在当前模式。
- Wi-Fi 配置模式下，`status link`、`status rtcm`、`bt`、`rtcm`、`alarm` 及工厂配对、白名单和报警覆盖操作返回 `ERR unavailable in wifi mode`。组合 `status` 报告在对应段显示不可用并继续输出系统状态。工厂 SN、调试等命令按其实际目标模块检查就绪状态。

## P2 台架验收步骤

1. 使用 DEV 镜像冷启动，检查启动日志和 `status sys` 的 `radio=bt reason=default`。记录 `sys mem` 的 free、largest 和 min。
2. 在蓝牙模式用手机连接并连续下发 RTCM 10 分钟，GNSS 输出设为 1 Hz。检查 RTCM 转发并记录 `sys mem` 的历史最低空闲堆，门槛为 40 KiB。
3. 执行 `radio wifi`，确认重启前收到完整的 `OK`。重启后检查 `radio=wifi reason=console`，扫描确认蓝牙广播消失，检查 `status gnss` 进入 running。待 GNSS 就绪后记录 `sys mem` 的 free、largest 和 min，与同条件下的 BT 启动值对比，确认 Wi-Fi 配置模式的空闲堆更大。
4. 在 Wi-Fi 配置模式执行 `status link`、`bt`、`factory pair` 及 `factory wl-clear`，检查均返回 `ERR unavailable in wifi mode`。
5. 执行 `radio bt`，检查重启后 `radio=bt reason=console`，确认蓝牙广播、手机连接和 RTCM 转发恢复。
6. 再次执行 `radio wifi`，确认进入该模式后断电。重新上电应显示 `radio=bt reason=default`，蓝牙广播恢复。

## 契约与待验收项

本卡的晶片实测待 P2 验收，包括 RTC 保留跨重启、实际串口回执和射频状态、以及两种模式的空闲堆。W2 负责 SoftAP、HTTPD、WebSocket 与空闲回落。本次冻结校验通过，交付为工作树改动。
